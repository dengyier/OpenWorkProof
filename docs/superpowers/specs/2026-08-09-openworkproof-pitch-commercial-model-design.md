# OpenWorkProof 路演商业模式重构设计

日期：2026-08-09
适用文件：`OpenWorkProof_港科大参赛暨天使轮融资路演_V2_含市场分析.pptx`

## 1. 沟通目标

路演结束时，非技术投资人应能回答四个问题：

1. 谁会为 OpenWorkProof 付钱；
2. 对方具体购买什么交付物；
3. 为什么这笔钱能够帮助对方上线、验收或回款；
4. 一次性项目收入怎样演进为年度授权和平台收入。

商业叙事不把开源协议、社区反馈、测试通过或市场规模等同于收入、订单、客户验收或商业成熟度。

## 2. 商业路径选择

### 2.1 首要付费主体

首要付费主体锁定为：**服务企业客户的 Agent 平台公司、企业 AI 解决方案商和系统集成商**。

典型合同发起人与预算来源：

- Agent 平台公司的产品负责人、解决方案负责人或企业业务负责人；
- AI 解决方案商的项目交付预算、产品化预算或企业客户专项预算；
- 信息安全、合规和法务是采购影响者与共同验收方，不默认是第一张采购单的唯一预算拥有者。

### 2.2 最终使用与验收主体

最终使用方是金融、医疗、制造、央国企等高责任场景的企业 AI 团队。其安全、IT 治理、合规、内审或业务负责人负责定义和确认验收边界。

### 2.3 渠道主体

安全服务商、审计机构、合规咨询公司和 Agent 框架生态属于后续渠道与合作伙伴，不作为早期主要收入假设。

## 3. 为什么付费

付费动机不表述为“购买一个开源协议”，而表述为解决 Agent 项目从 PoC 到正式交付之间的责任与验收阻断：

- 项目能够运行，但企业无法证明每项行为由谁授权、是否越权；
- 日志能够查看，但无法由独立第三方离线复核；
- 技术结果通过，但安全、合规或业务方缺少可签署的验收依据；
- 项目因此延迟上线、尾款结算或复制到高责任客户。

OpenWorkProof 的付费价值是把一次 Agent 工作流变成可授权、可复核、可验收和可结算的商业事实，从而帮助方案商缩短上线周期、降低责任争议并提高高责任行业项目成交率。

## 4. 首笔交易闭环

首笔交易采用一条具体工作流的“可信交付改造包”，而不是企业级大平台：

1. Agent 方案商提供真实项目、目标工作流和客户验收要求；
2. OpenWorkProof 完成授权边界、角色分权、证据槽位和验收规则设计；
3. 交付 Agent 适配器、签名回执链、离线证据包与验收报告；
4. 企业客户的安全、合规或业务 Acceptor 完成接受或拒绝；
5. 方案商据此完成正式交付与项目结算。

首笔交易的最低证据包括：付费合同或采购凭证、真实工作流、双方确认的验收标准、交付结果和验收结论。没有这些证据时，只能称为价格与路径假设。

## 5. 收入阶梯

以下价格用于路演中的商业验证设计，不代表现有报价、合同或收入：

| 阶段 | 购买内容 | 价格假设 | 验收结果 |
|---|---|---:|---|
| 可信交付诊断 | 工作流风险诊断、协议适配方案、验收指标 | 3—5 万元 | 风险清单、目标架构与验收基线获确认 |
| 付费 PoC／改造包 | 契约、权限策略、Agent 适配器、证据包、验收报告 | 20—50 万元／项目 | 指定工作流可生成并离线验证完整证据包 |
| 企业年度授权 | 多工作流治理、SDK、升级支持、年度证据治理 | 30—100 万元／年 | 约定范围内持续运行与周期性治理报告 |
| 平台 OEM／SDK | 将可信交付能力嵌入 Agent 平台 | 50—150 万元／年起 | 平台企业客户可调用、验证和导出证据 |

收入演进逻辑为：**诊断发现边界 → 付费改造验证价值 → 年度授权形成持续收入 → OEM/SDK 放大分销**。

## 6. PPT 第 12—15 页重构

### 第 12 页：谁付钱，以及为什么现在付

标题：**第一张采购单，来自需要通过企业验收的 Agent 方案商**

主要内容：

- 中央呈现“Agent 方案商”作为付款主体；
- 左侧呈现其企业项目和待收尾款；
- 右侧呈现终端企业的安全、合规和业务 Acceptor；
- 底部用一句话完成闭环：没有可信验收，PoC 难以上线，方案商也难以结算。

### 第 13 页：买什么，以及怎样形成复购

标题：**不卖抽象协议：从一条工作流改造，走向年度治理授权**

主要内容：

- 展示诊断、付费 PoC、年度授权、平台 OEM 四级收入阶梯；
- 每一级同时展示交付物、验收结果和价格假设；
- 明确服务切入是为了发现可复制边界，不是长期停留在纯咨询。

### 第 14 页：壁垒与主体关系

保留协议中立性、角色分权、证据模板和开源社区四类壁垒；强化“开源协议形成信任，企业产品与实施形成收入”。保留参赛主体、研发/IP/融资主体和技术 Owner 的既有确认口径。

### 第 15 页：融资如何验证商业模式

保留天使轮融资 200 万元和 15 个月窗口；将商业目标明确为：

- 3 个付费 PoC；
- 1 个可公开参考客户；
- 1 个年度授权客户；
- 验证真实客单价、销售周期、交付成本和续费理由。

资金用途继续使用既有 40% 产品与协议研发、30% 企业试点与交付、15% 安全/法务/IP、10% 市场与社区、5% 储备资金结构。

## 7. 叙事衔接

市场规模页回答“预算池为什么正在形成”；产品与案例页回答“项目是否具备可信交付能力”；商业模式页回答“谁把预算转成采购单”；融资页回答“200 万元将验证哪些尚未成立的商业假设”。

四段叙事必须区分：市场信号、工程能力、社区反馈、真实商业验证。

## 8. 证据边界

- 社区评论证明问题受到讨论，不证明客户采购；
- 两个开源 Issue 证明协议可复核，不证明企业生产验收；
- 测试和离线验证证明工程层状态，不证明收入；
- 所有价格、转化率、年度授权和三年收入均标注为待验证假设或经营目标；
- 未取得付费合同前，不使用“已有客户”“商业闭环已验证”或“形成收入”等表述。

## 9. 完成标准

- 非技术读者能在 30 秒内指出首要付费主体；
- 商业模式页同时回答买什么、为什么买、如何验收、如何复购；
- 融资金额与 15 个月商业里程碑直接对应；
- 第 12—15 页与前后页面叙事连续，没有重复或相互冲突；
- 全部 16 页通过逐页视觉检查、溢出检测、来源备注和文件完整性检查。

## 10. 非目标

- 本轮不把项目改造成完整 SaaS 产品规划；
- 不虚构客户、合同、收入、转化率或客户评价；
- 不扩展新的市场规模模型；
- 不改变已确认的参赛主体、融资主体和技术 Owner。
