# OpenWorkProof README 人本工程叙事设计

> 日期：2026-08-24
> 状态：用户已确认叙事方向，待书面规格复核
> 修改对象：`README.md`、`README_en.md`
> 核心取向：企业负责人先看懂价值，开发者随后获得完整接入路径

## 1. 目标

重写 OpenWorkProof 中英文 README，使第一次接触项目的人能够依次回答四个问题：

1. OpenWorkProof 为什么存在；
2. 它解决什么具体问题；
3. 它现在真实做到了什么；
4. 我如何安装、验证、接入或参与。

README 既要有人的立场，也要有工程证据。情怀来自项目真正守护的价值，不来自空泛的
行业口号。

## 2. 核心叙事

项目箴言：

> 让智能依人的目的而行动，让每一次行动经得起人的判断。

哲学表达：

> 能力回答“能做什么”，目的回答“为何而做”，责任要求行动能够被解释、验证与接受。
>
> 当 AI 开始替人行动，人的意图不能退化为一行提示词，授权不能变成一次默认同意，
> 最终判断也不能在自动化流程中悄然消失。

产品定义：

> OpenWorkProof 是 AI Agent 工作的开放验证协议。它把人的目的、授予的权限、
> Agent 的行动、留下的证据和最终验收连接成一条可独立验证的工作链。
>
> 它不替人判断什么是善，也不承诺 Agent 永远正确。它做的是更基础的工作：
> 让每一次重要行动都说明自己为何发生、依据什么权限、产生了什么结果，并把接受、
> 拒绝、撤销和申诉的权利留给人。

贯穿全文的判断：

> OpenWorkProof 关心的，不只是 Agent 是否完成了工作，而是这项工作是否忠于人的目的，
> 遵循正当的授权，并经得起独立的验证与人的最终判断。

README 不承载创始人的全部人生使命，也不展开星火、OPC、天机、GEO 或其他项目。
OpenWorkProof 只承担其中一个明确命题：当人把工作交给 AI，人的授权、知情、拒绝、
撤销、申诉和最终验收权仍然可以被机器验证。

## 3. 读者顺序

### 第一层：企业负责人和业务决策者

先用业务语言解释：Agent 声称完成工作，不等于这项工作经过授权、过程可信、结果已经
验收。企业购买的不是密码学，而是更低的复核成本、更清楚的责任边界和更敢委托工作的
条件。

### 第二层：开发者和架构师

随后提供协议对象、状态链、Human Agency Profile、离线验证、CLI、MCP、AgentTeams
和 Python API 的准确入口。

### 第三层：开源贡献者和协议同行

最后说明当前边界、路线图、贡献方式和开放协议的公共价值。

## 4. README 结构

### 4.1 第一屏

包含：

- 项目名；
- 中英文切换；
- 一句使命；
- 一句产品定义；
- 安装、快速验证、协议文档三个入口；
- 许可证、PyPI、MCP Registry、测试状态等必要链接；
- 本地候选与公开发布状态的精确区别。

第一屏不出现长篇版本历史、商业套餐、融资信息或十个以上协议名词。

### 4.2 为什么存在

用三到五个自然段说明：

- MCP 连接 Agent 与工具，A2A 连接 Agent 与 Agent；
- 连接层不能独立回答授权、执行、验收和责任问题；
- OpenWorkProof 不让 Agent 更聪明，而是让 Agent 工作更值得信任；
- 可信不是默认相信某个平台，而是任何持有证据包与公钥的人都能独立复核。

### 4.3 一个具体问题

以“Agent 说任务完成了”为起点，提出具体问题：

- 谁授权它做这件事；
- 它有没有越过路径、工具、配额或期限；
- 补丁、测试、报告是否属于同一条因果链；
- 验证通过与客户接受是否被错误混同；
- 纠纷发生后，第三方是否能离线复核。

### 4.4 是什么，也不是什么

OpenWorkProof 是：

- 工作契约与可验证执行协议；
- 签名授权、行动凭证、因果证据和独立验收的组合；
- 可嵌入现有 Agent、CI、MCP 和多 Agent 编排器的开放层。

OpenWorkProof 不是：

- Agent OS 或新的模型框架；
- 员工监控、绩效评分或自动问责系统；
- 支付托管、法律仲裁或合规认证；
- 声称能判断业务结果绝对正确的系统。

### 4.5 工作原理

用一张短流程和一个紧凑表格解释：

```text
WorkOrder -> CapabilityGrant -> PolicyDecision -> ActionReceipt
          -> VerificationDecision -> AcceptanceDecision
```

正文只解释读者必须理解的对象。完整 schema、状态机和版本细节链接到 `specs/`、
`docs/protocol/` 和 `docs/status.md`。

### 4.6 Human Agency

这是新版 README 的独特章节。必须说明：

- CapabilityGrant 表达系统授予的能力；
- HumanAgencyProfile 表达人愿意让 Agent 自主使用其中哪些能力；
- 有效权限取 WorkOrder、Grant 和 active profile 的交集；
- reserved decision 在执行前拒绝；
- appeal 只请求复核，不自动恢复权限；
- 只有 Acceptor 签名的 transition 能撤销或替换 profile。

该章节不得宣称法律责任被自动转移，也不得把人类签名解释为判断正确。

### 4.7 五分钟快速开始

保留最短可运行路径：

1. 安装；
2. 验证 CLI；
3. 运行最小样例；
4. 验证离线包；
5. 链接到完整开发文档。

首页不复制所有 CLI 与 Python API 示例。详细内容移交现有文档，避免 README 超过读者
的注意力预算。

### 4.8 接入方式

用一个表格对照：

- GitHub Action：现有交付流程；
- CLI：本地验证与自动化；
- MCP：工具协议接入；
- AgentTeams：多角色协作；
- Python API：深度嵌入。

每种方式只保留一个入口命令或文档链接。

### 4.9 已有证据

保留可复核事实：

- Rich #4196、Dify #33013、AgentScope #2239 等自有演示或验证案例的准确边界；
- current required-live `4265 passed / 0 failed / 0 skipped`；
- current candidate `183 passed / 0 failed / 0 skipped`；
- 真实三 Agent preflight 已通过；
- 离线 bundle、不可变 inventory 与供应链门已验证。

必须同时说明：真实客户采用、付费、外部人工 Acceptor、生产部署和上游采纳仍然没有
证据时，不得用案例、客户、落地或生产验证等词替代。

### 4.10 商业入口

只保留 Verified Agent Delivery 的最小定位：把一次 Agent 工作转换为可验证、可由客户
独立验收的交付事实。不得把 settlement readiness 写成已经付款，不在 README 展开套餐
定价、市场规模或融资叙事。

### 4.11 路线图与参与方式

路线图区分：

- 已完成工程能力；
- 下一步协议闭包；
- 需要外部参与的生态验证。

参与方式包括使用、报告问题、实现适配器、审阅 schema、复现实验和贡献代码。

### 4.12 结尾

中文结尾从项目箴言回到现实委托：

> 我们希望未来的 Agent 可以承担越来越多的工作。能力越强，越应该忠于人的目的；
> 系统越自动，授权、证据和申诉越不能消失。
>
> OpenWorkProof 想做的事情很朴素：当人把工作交给 AI，仍然知道自己交出了什么、
> 发生了什么，以及何时可以说“不”。让智能依人的目的而行动，让每一次行动经得起
> 人的判断。

英文版主句为：

> Let intelligence act toward human purposes, and let every action stand up to human judgment.

英文全文传达同一意义，但按英文开源社区的自然表达重写，不逐句直译。

## 5. 写作规则

1. 先说人话，再给术语；术语第一次出现时必须解释。
2. 不把同一个判断在版本、商业、愿景三个章节重复陈述。
3. 不使用虚构案例、模糊市场数字或未经回读的外部采纳信息。
4. 不使用口号堆叠、过量粗体、emoji 或广告式形容词。
5. 不使用破折号制造戏剧感；通过句子结构表达节奏。
6. 中文自然、克制、有立场；英文简洁、直接、适合国际开发者阅读。
7. README 描述项目当前是什么，不以提交差异或历史修改过程组织正文。
8. 历史版本测试快照保留在 `docs/status.md`，README 只保留当前值和一个必要的公开发布边界。

## 6. 信息架构边界

README 目标长度为：

- 中文约 450 到 600 行；
- 英文与中文章节语义一一对应，允许因语言习惯调整段落；
- 详细 CLI、MCP schema、Python API、版本历史和逐项测试记录通过链接进入专门文档。

不得为了缩短 README 删除以下内容：安装入口、最小验证路径、Human Agency、离线验证、
当前证据、诚实边界、许可证、贡献方式和安全报告入口。

## 7. 验收标准

完成后必须满足：

1. 企业负责人阅读前 150 行即可理解购买价值与边界；
2. 开发者不离开 README 即可完成安装和第一个本地验证；
3. 中英文核心事实、版本、测试数字与边界一致；
4. 所有相对链接存在，所有代码块闭合；
5. `tests/test_documentation_boundaries.py` 通过；
6. `git diff --check` 通过；
7. README 不出现客户采用、付款、托管、法律合规或外部验收的无证据主张；
8. 通读后能感受到项目守护人的决定权，但不会误以为它是哲学宣言或社会治理平台。

## 8. 明确不做

- 不修改协议代码、schema、测试实现或 candidate inventory；
- 不改变版本号、PyPI 发布状态或 MCP Registry 公共状态；
- 不新增定价、融资和市场规模章节；
- 不把其他星火项目并入 OpenWorkProof 产品叙事；
- 不凭 README 改写任何商业或外部采用事实。
