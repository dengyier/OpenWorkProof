## Bug 描述

Dify v1.14.0-rc1 重构了 `LLMNode.invoke_llm` 的签名：将 `structured_output_enabled` / `structured_output` 两个 keyword 参数统一为 `structured_output_schema`，但 `QuestionClassifierNode` 的调用方未同步更新。任何包含问题分类器节点的工作流执行时报：

```
TypeError: LLMNode.invoke_llm() got an unexpected keyword argument
'structured_output_enabled'
```

## 为什么选 Dify

与 Rich #4196（开发者工具库）不同，Dify 是 **用户交互的 AI 工作流平台**——终端用户在编排 workflow 时加了个节点就崩溃了。这是真正的应用层 bug，且与 OpenWorkProof 的使命（验证 AI Agent 工作）产生元层面闭环。

### 协议层 (5 测试)

完整九步五角色证据链，与 M2 (Rich #4196) 同构：

| 步骤 | 角色 | 操作 | 验证点 |
|------|------|------|--------|
| 1 | Maintainer | WorkOrder 初始化, running 状态 | 根授权激活 |
| 2 | Developer | `owp.repo_read` | 输出摘要精确匹配候选文件 SHA256 |
| 3 | Developer | `owp.apply_patch` | 补丁证据字节等同上游 fix；`requested_paths` 与 `resolved_entries` 经权威回放校验 |
| 4-5 | Verifier | `owp.run_tests` → locally_verified | 本地验证完成 |
| 6 | Manager | `compose_proof` → evidence_incomplete | 首次组合报告标记缺独立验证 |
| 7 | Manager | recompose → proof_ready | 独立 Verifier 补充后，证据闭合 |
| 8 | Acceptor | 外部 TCP 子进程签名 → accepted | 真实 Ed25519 签名，awaiting_human → accepted |
| 9 | 离线方 | `verify_acceptance_bundle` | 不接入任何一方系统，离线验签通过 |

## 关键修复

`_validate_authoritative_receipt_predicates` 在 `1d511d3` 后扩展覆盖了 `owp.apply_patch`。M3 的 `path_allowed` 谓词需同时更新 `requested_paths` 和 `resolved_entries`（而非仅 `resolution_manifest_digest`），以匹配权威回放从 `receipt.request_arguments.target_paths` 推导的精确路径。
